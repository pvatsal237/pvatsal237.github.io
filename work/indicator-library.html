BI governance · Power BI catalogue

How many reports, models and indicators do we have, and which one is right?

Anyone new to a BI team hits the same wall: there is no single place that lists every report, semantic model and indicator, what each one means, or which copy is official. I built the Indicator Library to fix that. It reads Power BI's own metadata, never the data, and builds one searchable catalogue that rebuilds itself on demand.

Key findings

  1. 13 of 23 indicators built in more than one model are calculated differently, so two reports can show different numbers for the "same" indicator.
  2. Only half of the indicator definitions have a written description, and 3 models were showing stale numbers after failed refreshes.
  3. Two measures checked a hard-coded login inside DAX, a security rule that belongs in row-level security instead.
01 · THE PROBLEM

Reporting grew report by report, and nobody had the full map

New staff learned by asking around. Simple questions took days: where does this number come from, which report is the official one, when was it last refreshed, and why do two reports disagree?

The Indicator Library answers those from Power BI itself. It compares every copy of an indicator side by side, its DAX and its source tables, and gives each one a verdict.

A copy "matches" only if both the DAX logic and the source tables are the same after normalizing names and whitespace.

02 · TWO EDITIONS

A plain-language viewer for everyone, a full catalogue for the BI team

The Viewer lets any staff member search an indicator and see its definition, numerator and denominator, source system, owner, which reports carry it and when it was last refreshed. It shows no SQL, servers or DAX, and a built-in check stops the build if any technical name leaks into it.

The catalogue adds the technical detail: source tables, refresh health, a reliability score for each copy, a recommended copy to keep, and a prioritized list of asks for owners.

Safety by design

  • Reads definitions, layouts and counts only, never table rows, using the analyst's own read access.
  • No credentials in files; anything in M code that looks like a password or account number is masked before the catalogue is built.
  • Changes to live models only after owner approval, one model at a time, with an undo history.

How I built it

  • I defined the problem, the design and the rules: what to catalogue, what new staff need to see, what counts as a duplicate, and what must never be read.
  • I used Claude for AI-assisted development of the code, then reviewed and tested the output: totals reconciled, the leak check passed, every page checked.

Limits of this demo

  • The estate is synthetic, shaped like a real one, so the findings show what the tool reports, not a real organization's results.
  • Reports are linked to indicators through the models they use; which visuals actually show an indicator is not harvested yet.
  • Tenant-wide coverage needs the Fabric admin Scanner API; without it, the catalogue covers the workspaces the analyst can open.
