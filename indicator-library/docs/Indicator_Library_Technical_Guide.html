Indicator Library: Technical Guide

How the catalog is built, how it pulls metadata from Power BI and Fabric, how lineage and descriptions are produced, and how model standards are written back safely.

1. Purpose and scope

The Indicator Library is an automated catalog of every Power BI report, semantic model, table and measure in 10 workspaces, traced back to its SQL, file or upstream-model source. It is rebuilt from the Power BI and Fabric REST APIs whenever we run it, so nobody has to keep it up to date by hand.

Design principle: metadata only. The library reads definitions (TMDL, Power Query M, DAX, refresh metadata). It never reads data rows. No customer or record-level data is retrieved, stored or shown at any step.

Scope. The workspaces listed in catalog_data/workspaces_keep.txt: Outage Management, Outage Management - Test, Customer Operations, Safety and Compliance, Field Services, Finance and Planning, Storm Response, Community Reliability, Executive Scorecards, Analytics Playground. Every phase, the workspace menu and the analysis honour this file. Deleting it includes every workspace the signed-in user can reach.

Questions it answers: where an indicator comes from; which models define it and whether those definitions agree; which reports are built on that model; when it last refreshed and on what schedule; who configured the model; which reports and models are duplicates or failing.

2. Architecture

Four read-only online phases pull definitions into CSVs. Four offline phases turn those CSVs into the pages in seconds. A separate local working copy, with Git as the undo, is the only route back to the service.

Every phase is its own Python script under harvest/, run in order by run_all.ps1. update-data.bat is the one-click wrapper. The pages are static, self-contained HTML: no server, database or application code is needed to read them.

4. Sign-in and API access

The harvest runs as the signed-in user, so it sees exactly what that person can already see in Power BI.

Sign-in (harvest/fabric_common.py)

  • azure-identity InteractiveBrowserCredential opens one browser sign-in per run.
  • TokenCachePersistenceOptions(name="indicator_library") keeps tokens in the operating system's encrypted token cache.
  • After the first sign-in an AuthenticationRecord is saved to .auth_record.json. It holds account and tenant ids only, no tokens. Each phase is a separate Python process and reuses the cached sign-in silently through this record.
  • Azure AD rejects one request spanning two resources, so the interactive sign-in asks for the Fabric scope only. The Power BI token is then obtained silently from the cached refresh token.
APIBase URLScopeUsed for
Power BI RESThttps://api.powerbi.com/v1.0/myorghttps://analysis.windows.net/powerbi/api/.defaultWorkspaces, reports, datasets, datasources, refresh history and schedules
Fabric RESThttps://api.fabric.microsoft.com/v1https://api.fabric.microsoft.com/.defaultgetDefinition (read) for models and reports; updateDefinition (guarded push only)

Reliability

  • fabric_request() retries up to 6 times on HTTP 429, 502, 503 and 504, sleeping for the Retry-After header (default 30 s).
  • Long-running operations (HTTP 202) are followed through x-ms-operation-id: poll /operations/{id} until Succeeded or Failed, then fetch /operations/{id}/result. Timeout 300 s per item.
  • Errors are recorded with their errorCode and message (phase1_errors.csv, model_status.csv) instead of stopping the run.
  • map_with_progress() prints the running count, elapsed time and an ETA roughly every 5%.

Environment. Windows, Python 3.10+ in a local .venv, no admin rights. Pinned packages in requirements.txt: azure-identity 1.27.0, msal 1.39.0, msal-extensions 1.3.1, requests 2.34.2, tzdata, openpyxl 3.1.5. The offline phases use only the Python standard library (plus openpyxl to read the owner worksheet).

Phase 2 in detail

  1. Runs 4 models in parallel (ThreadPoolExecutor, MAX_WORKERS = 4).
  2. Decodes the Base64 definition parts and parses the TMDL with a small indentation-aware parser: quoted names, multi-line DAX and M, and properties such as description, displayFolder, formatString, isHidden.
  3. Extracts measures; tables with partition type and mode; columns with data type and calculated flag; relationships (from/to, cardinality, cross-filter, active); partitions (M code, DAX or Direct Lake entity); shared expressions and parameters.
  4. Redacts any M or DAX line that looks like an embedded credential, replacing it with // [line redacted: possible credential] and setting possibleSecret = true.
  5. Saves the complete definition (TMDL, definition.pbism, .platform) to definitions/<workspace>/<model> (<id8>).SemanticModel/, replaced each run and git-ignored.
  6. Records success or the error code per model in model_status.csv. All 25 models in scope were read in the last run.

Full or partial refresh

  • update-data.bat calls run_all.ps1 -Choose, which lists the workspaces from the last workspaces.csv as a numbered menu. Enter means all.
  • The selection reaches every phase as the LIB_WORKSPACES environment variable (names separated by |).
  • write_merged_csv() rewrites only the chosen workspaces' rows and keeps every other workspace's previous rows, so skipping a workspace never loses its data.
  • Report usage (pages, visuals, which visual uses which measure) was a separate phase until 2026-11-13. It was retired because it took about a third of the run time and the team does not need visual-level detail.

6. Phase 4: lineage and analysis (offline)

phase4_build_data.py traces every measure to the physical tables it depends on and writes one bundle, report_data.json. It runs in seconds with no network.

Step 1: find each table's source from its M code

  • Sql.Database(server, db), and Sql.Databases(server) followed by Source{[Name="Db"]}[Data], with server and database resolved through model parameters.
  • [Schema="…", Item="…"] and [Name="…", Kind="Table|View"] navigation steps give schema and table.
  • Native queries (Query="…"): the FROM and JOIN tables inside the SQL text are extracted.
  • Excel.Workbook sheets and tables, SharePoint.*, CSV, folder, ODBC and web sources.
  • Direct Lake entities (OneLake / Fabric endpoints).
  • DirectQuery to another published model (DirectQuery to AS - …) is recorded as a Power BI model source: upstream workspace, model and table, linked to the upstream model when it is in scope. These are not listed as SQL tables.
  • References to other queries in the same model are followed, so a table built on a staging query inherits that query's source.

The database is cross-checked against the service's datasource list from phase 1, which removed earlier blank databases. Each source is split into server, database, schema and table.

Step 2: walk each measure's DAX

  1. Strip comments and string literals, then collect table references ('Quoted Table'[…], Table[…]) and bare measure references ([Measure]).
  2. Keep only names that are real tables in that model, and add the measure's home table.
  3. Map each table to its physical sources (SQL, Excel, SharePoint, CSV, folder, ODBC, web, Direct Lake, Power BI model).
  4. Recurse into each referenced measure, with a visited set to stop cycles, and union the sources and tables.

Step 3: compare indicators that share a name

  • Each measure gets a DAX hash: whitespace-normalised, lower-cased DAX, MD5, first 8 characters. Names are normalised the same way.
  • Measures with the same normalised name in different models form a group. A different hash or a different source set within a group marks a variant.
  • Helper measures (names starting with _, plus refresh timestamps) are flagged as utilities and left out of alignment counts: 7 of 115.

Step 4: assemble the bundle

Models (storage mode, refresh status and schedule, configured-by, report count), reports (model, web link), tables, sources and measures are indexed into compact JSON. Indicators are linked to the reports built on the same model and labelled "available", not "used", because visual usage is not harvested (hasUsage = false). --no-owners leaves owner emails out.

8. Privacy and safety controls

Much of our data is customer and operational information, so safety is built into every phase rather than left to the reader.

Metadata only

Only definitions and refresh metadata are requested. No DAX query, no row read, no sampling, at any phase.

Credential redaction

M or DAX lines that look like an embedded credential are replaced and flagged during parsing (phase 2).

Identifier masking

Customer account number patterns found inside DAX or M are masked, and counted per model (phase 4). The patterns are never printed.

Manual tables dropped

Typed-in "Enter Data" table payloads are never copied; tables of selected record numbers are removed entirely.

Two separate builds

The viewer page is built from its own reduced data file, not a hidden switch on the full page: a switch would still send the full data to every viewer.

Build-time leak audit

Phase 4b fails the build if any server, path or source-object name from the full bundle appears in the viewer file.

Sharing rule

Team pages contain server names, DAX and owner emails: Internal, team only, git-ignored. -NoOwners removes emails.

Push refusal

Items with identifier-like literals (standards rule L18) are refused by the shared-copy step and by the push script.

Desktop cache

Desktop's .pbi cache file can hold model data; it is never opened, copied or shared by any tool.

No "view-only HTML" exists. A browser must receive data to render it, so right-click or save blocking is not a control. The real controls are sending less data (the viewer build) and hosting behind authentication (planned, section 17).

10. Measure descriptions pipeline

81 of 115 measures (70%) had no usable description. Phase 4c proposes one for each; owners decide; the pages show where each description came from.

Phase 4c: describe_measures.py

  • Reads the bundle (DAX with identifiers already masked, lineage) and columns.csv (names, types, descriptions). No data rows.
  • Writes the wording from the measure name, its DAX pattern, the tables and columns it reads, and a utility reliability glossary (SAIDI, SAIFI, CAIDI, OMS, EAM, restoration time).
  • Never states a local definition the DAX does not show.
FieldValues
statusexisting (keep the model's text) · propagated (an identical copy elsewhere already has a good description) · generated · improved (existing text only repeated the name, was a few characters, or had a broken character)
confidenceHigh · Medium · Low (dynamic or complex logic: owner confirms)
review_noteWhat an owner must confirm for externally defined indicator families, plus data-grain or privacy caveats
logic_groupGroups identical logic so one decision covers every copy

Owner review and overlay

  1. build_description_worksheet.py writes Measure_Description_Worksheet_<date>.xlsx with sheets Read me, By model (live progress counts), Definitions to confirm and Review. It refuses to overwrite a worksheet that has entries.
  2. Owners set Decision (Accept / Edit / Reject / Needs SME) and, for Edit, a Final description.
  3. description_overlay.py, called by phase 5, merges by (workspace, model, table, measure) in order of trust: owner decision, then the model's own text, then the proposal.
  4. The Model View shows ✓✓ owner-approved, ✓ in the model, ~ proposed (not yet reviewed), — none, with a filter and a proposed-% summary.
  5. Writing approved text into the models is a separate, deliberate step: apply_descriptions.py then push_definitions.py (section 12).

12. Write-back workflow: fixing models in bulk, safely

The catalog shows what to fix. The write-back tools fix it on a local copy, with Git as the undo, and only one script can send a change to the service.

#CommandWhat it doesWrites to the service?
01update-data.batRefresh the catalog and pagesNo (reads)
02pull_items.pyDownload report(s) and the model each reads into pbip_working/ (own Git repo). Records the service hash in _state.json; refuses to overwrite local edits unless --forceNo (reads)
03bulk_standards.pyDisplay folders from standards_folders.csv, naming checks from standards_naming.csv, date table only with --fix-date-table. Dry run writes standards_preview.txt and standards_findings.csvNo (local + Git)
04apply_descriptions.pyOwner-approved descriptions into the /// lines of the TMDL files; backup of each changed fileNo (local + Git)
05edit_in_desktop.py start|finishBuilds pbip_edit/ where the report points at the local model (byPath), so Desktop edits files, not the service. finish shows the diff; --apply copies back and commitsNo (local + Git)
07stage_standards.py, review_worksheet.py, bpa_audit.pyStage every pulled model with standards and compare; Standards_Review.xlsx for per-model decisions; 12 custom governance BPA rules with a simulated audit and Excel summaryNo
08typo_scan.pyCandidate typos: a word used once or twice that is 1–2 letters from a word used 3+ times. Owner renamesNo
06push_definitions.pySend one item's definition (Fabric updateDefinition)Yes, guarded

How a push is protected

  1. Needs --model or --report: one named item per run.
  2. Re-reads the item from the service and compares it with the hash recorded at pull time. If someone changed it since, it stops and lists the differing files.
  3. Without --apply it stops here and prints the file-level differences.
  4. With --apply it asks you to type the item's name, commits to Git, sends the definition, downloads it again and verifies it, then records the new hash.
  5. The service rewrites files in canonical order, so the comparison is on content, not byte order; the service form is then adopted locally.
  6. Items flagged by the identifier check are refused.

Rules for every command

  • Metadata only; never open or share Desktop's cache file.
  • Dry run first; read the preview before --apply.
  • Nothing is renamed automatically; naming findings are report-only and list what a rename would touch.
  • Only push_definitions.py writes to the service, and only when the user asks for that item.
  • Pilot in the test workspace first, one model, before any other workspace.
  • After a push, the owner's PBIX on SharePoint is no longer the working copy: republishing it would overwrite the change. Tell the owner first.

Each command has a directive in docs/directives/ that states when to use it, the exact command, what it reads and writes, how it protects you and how to undo it.

15. Runbook

# once
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# refresh (menu, Enter = all)
update-data.bat

# named workspaces, no menu
powershell -File run_all.ps1 -Workspaces "Outage Management","Outage Management - Test"

# rebuild pages from existing CSVs (seconds, no sign-in)
powershell -File run_all.ps1 -RebuildOnly

# leave owner emails out
powershell -File run_all.ps1 -NoOwners

After a refresh

  1. The console ends with Done in N min and a Descriptions: … owner-approved, … from the model, … proposed only line. A yellow "Phase 4c … skipped" warning means pages were built without proposals: re-run -RebuildOnly.
  2. Open both team pages in Edge or Chrome and check the generated date is today.
  3. New owner decisions in the worksheet only need -RebuildOnly.
  4. Update docs/PROJECT_STATUS.md; share HTML files only inside the team.

Filling business context

  • Business definitions: copy business_context_TEMPLATE.csv to business_context.csv, fill it, rebuild.
  • Report descriptions, owners and hide flags: copy report_context_TEMPLATE.csv to report_context.csv, fill it, refresh.
  • Scope: edit workspaces_keep.txt, then refresh.

Roadmap

  1. Hosting. IT request for an internal IIS site with Windows authentication: viewer edition at /, team edition at /team/, each limited to its own AD group, static files only.
