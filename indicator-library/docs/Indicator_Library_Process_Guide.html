The big picture

A script signs in as you, asks the Power BI and Fabric REST APIs for the definitions of every report and model you can reach, and turns the answers into tables. Those tables are analysed and rendered as one standalone HTML catalog.

How a REST call works

Click a numbered arrow (or use Next) to see what is sent, what comes back, and why. Two APIs are used: Power BI REST for inventory and Fabric REST for full definitions.

What the data looks like

Every file in catalog_data is one table in this model. The keys (workspace, report, model, table, measure) are what let the catalog answer "where does this indicator sit?".

How to use it for a report catalog and indicator library

The same tables support several jobs. The catalog tells you what exists; the library work is deciding which definition is the right one.

1. Report catalog

One row per report: workspace, model it reads, pages, visuals, indicators used. Add owner and refresh health to make it a real directory.

Report: Reports tab · files: reports.csv, pages.csv, visuals.csv

2. Indicator library

One entry per indicator with its DAX, where it sits, and which reports use it. The goal is a single approved definition for each, with the copies pointing to it.

Report: Indicators tab · files: measures.csv, measure_usage.csv

3. Find conflicting definitions

Same name, different DAX or source tables. 13 of 23 repeated indicators differ in logic, source, or both. Start with the most repeated names.

Report: verdict filters on Indicators

4. Impact analysis

Before retiring or changing a source table, see every model, indicator and report that depends on it.

Report: Source tables tab · file: measure_lineage.csv

5. Quality and governance

Undocumented measures, unused measures, failing refreshes, file-based sources and manual tables, each as a worklist.

Report: Data quality tab

6. Self-service discovery

Anyone can search an indicator name and see where it is already built, instead of creating another copy.

Report: search box on any tab

Roadmap

Done

  • Workspace and report inventory (10 kept workspaces, 35 reports, 25 models)
  • Full model definitions: measures, tables, columns, relationships, M code
  • Refresh schedules and history, one sign-in per run, partial refresh by workspace
  • Model-centric view alongside the report-centric catalog
  • Source-table lineage and cross-model comparison
  • Standalone HTML report

Next

  • Add owners (workspace roles), parameters and dataflow lineage to the harvest
  • Add a hand-kept business context table: owner, plain-language definition, numerator and denominator, status, certified or not
  • Mark one canonical definition per repeated indicator and list the copies to retire
  • Work the conflict list, most repeated names first

Later

  • Schedule the harvest (for example a Fabric notebook) and store the tables in a Lakehouse
  • Build a Power BI report on those tables so the catalog lives where people already work
  • Compare each run with the last to flag new, changed and removed indicators
  • Ask for Fabric admin Scanner API access to cover the whole tenant, not only the workspaces you belong to

Access and safety

What your access can do

  • Works: workspace and item lists, data sources, refresh status, full model and report definitions, pages, refresh schedules and history, parameters, workspace roles, metadata-only DAX (INFO.VIEW.*).
  • Not available: admin and Scanner APIs, activity and audit events, workspaces you are not a member of, service-principal calls, gateway and capacity management.
  • Not used on purpose: any write operation, and report export as .pbix.

Safety rules the scripts follow

  • Definitions, layouts and counts only; never table rows.
  • No credentials in files. Sign-in is your own account; the token is held in the operating system's protected cache.
  • Manual (Enter Data) table payloads are dropped, and any M line that looks like a credential is redacted.
  • Model owner (configured-by) addresses are shown on the Models and Asks tabs so follow-ups have a name. Rebuild with phase4_build_data.py --no-owners to leave them out.
  • As in the report-catalogue SOP, customer account number patterns are masked in DAX and M code, and typed-in tables of record numbers are dropped. Any hits are listed on the Asks tab for the owner to fix at source.
  • The outputs include internal server and database names, so keep them inside the organization.

Re-run it

Double-click update-data.bat. It asks which workspaces to refresh (press Enter for all), signs you in once, runs the phases in order, and rebuilds every page. Workspaces you skip keep the data from their last refresh. A full run takes roughly 30 minutes to 2 hours (phase 2 is the long one); a few workspaces take far less. Each slow phase prints what it is doing, a running count and an estimated time left.

update-data.bat                                   # menu: pick workspaces, or Enter for all
powershell -File run_all.ps1 -Workspaces "Outage Management","Outage Management - Test"   # same, without the menu
powershell -File run_all.ps1                      # everything, no menu
powershell -File run_all.ps1 -RebuildOnly         # offline: rebuild pages from existing CSVs, seconds
powershell -File run_all.ps1 -NoOwners            # leave model owner emails out

# what run_all.ps1 runs, in order (harvest folder, using .venv):
phase0_workspaces.py     # workspace list, and the one sign-in
phase1_inventory.py      # reports, models, sources, refresh status
phase2_definitions.py    # measures, tables, columns, M code (slowest)
phase3_refresh_schedules.py    # refresh schedule and last 10 runs per model
phase4_build_data.py     # lineage, source systems, scrub
phase4b_build_viewer.py  # viewer edition data and leak audit
phase5_build_html.py     # report, viewer and model-view pages
One-time setup: create .venv and install requirements.txt (done on this machine). The sign-in is saved in .auth_record.json (account ids only, no tokens) plus the operating system's protected token cache, so phases after the first do not prompt again.
